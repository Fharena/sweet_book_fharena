# 5분 데모 스크립트

아래 스크립트는 발표자가 실제 화면을 넘기면서 바로 읽을 수 있도록 구성했습니다.  
흐름은 `업로드 -> 검토 -> 미리보기 -> 책 생성 -> 주문 -> 웹훅 운영` 순서입니다.

## 오프닝

안녕하세요. Triplogue는 여행 사진을 올리면 촬영 시간과 위치 정보를 읽어서 날짜별, 장소별로 자동 정리하고, 그 결과를 Sweetbook 포토북 주문 흐름까지 연결하는 서비스입니다.

이번 데모에서는 사진을 편집기로 오래 다루지 않아도, 여행 기록이 바로 책 초안이 되는 흐름을 보여드리겠습니다.

## 1. 업로드

지금 보시는 화면은 여행 사진 업로드 단계입니다.

갤럭시 사용자는 카메라 설정에서 위치 태그를 켜두면 EXIF의 GPS 정보가 더 잘 유지됩니다. 그래서 사진을 올리면 앱이 촬영 시간과 위치를 먼저 읽고, 가능한 경우 자동으로 여행 챕터 후보를 만들어 줍니다.

중요한 점은 위치 정보가 없는 사진도 막지 않는다는 것입니다. GPS가 빠진 사진은 수동 태깅 후보로 표시되고, 나중에 검토 화면에서 한 번에 보정할 수 있습니다.

## 2. 검토

다음은 검토 단계입니다.

이 화면에서는 자동으로 묶인 날짜와 장소를 확인하고, 위치 정보가 없는 사진을 직접 보정합니다. 수동 태그를 입력하고 여러 장을 선택한 뒤 한 번에 적용하면 draft와 챕터가 다시 계산됩니다.

즉, 자동 분류가 기본이지만 사용자가 마지막으로 이야기를 다듬을 수 있게 만든 화면입니다.

## 3. 미리보기

이제 포토북 미리보기 화면입니다.

여기서는 세 가지 디자인 패턴 중 하나를 고를 수 있습니다. `Timeline Classic`은 날짜 중심의 안정적인 패턴이고, `Postcard Map`은 장소와 지도를 강조합니다. `Photo Essay`는 사진을 크게 쓰는 편집형 패턴입니다.

이 화면에서 확인할 포인트는 표지, 스프레드 구성, 예상 페이지 수, 예상 금액입니다. 사진과 챕터 수가 바뀌면 이 예상치도 같이 반영됩니다.

## 4. 책 생성

미리보기가 마음에 들면 책 생성 단계로 넘어갑니다.

여기서는 테스트 책을 먼저 생성해 `bookUid`를 확보하고, 표지와 내지를 조립한 뒤 최종화까지 진행합니다. 책이 아직 준비되지 않았다면 먼저 테스트 책 생성 버튼을 눌러야 합니다.

이 흐름의 핵심은 브라우저에 API 키를 두지 않고, 모든 생성 요청을 서버 라우트를 통해 안전하게 넘긴다는 점입니다.

## 5. 주문

책이 최종화되면 주문 단계로 넘어갑니다.

배송지와 수량을 입력하고 주문을 요청하면, 서버가 `Idempotency-Key`를 붙여 중복 요청을 줄이고 Sweetbook 주문 API로 전달합니다. 이 단계에서는 실제 차감과 연결될 수 있으므로 최종화 상태와 입력값을 다시 확인하는 것이 중요합니다.

주문이 생성되면 checkout 화면에서 `orderUid`, 응답 상태, 차감 금액을 먼저 보여주고, 같은 화면 아래에서 웹훅 수신 로그를 15초 주기로 새로 읽어 이후 상태를 바로 추적할 수 있습니다.

## 6. 웹훅 운영

마지막으로 운영 화면입니다.

이 화면에서는 Sweetbook 웹훅 설정을 등록하고, 테스트 이벤트를 보내고, delivery 이력과 실제 수신 receipt를 함께 확인할 수 있습니다. 웹훅은 최초 등록 시에만 전체 `secretKey`가 노출되기 때문에, 이 화면은 운영 전환 전에 값을 확인하고 바로 보관하는 용도입니다.

웹훅 receipt까지 같이 보이면, 주문이 실제로 어떤 상태 이벤트를 받았는지 추적하기가 훨씬 쉬워집니다.

그리고 운영 패널에서 보는 수신 로그와 checkout에서 보는 주문 추적 카드가 같은 receipt 기준으로 연결되므로, 사용자 흐름과 운영 흐름을 함께 설명할 수 있습니다.

## 마무리

정리하면 Triplogue는 여행 사진을 단순히 보여주는 앱이 아니라, 사진을 날짜와 장소로 자동 정리하고 수동 보정까지 거쳐서 바로 포토북 주문으로 이어주는 경험을 목표로 합니다.

핵심은 편집을 길게 끌지 않고, 여행 기록을 빠르게 책으로 바꾸는 데 있습니다.

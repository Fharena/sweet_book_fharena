# 크리티컬 이슈 기록

## 2026-04-05 템플릿 파일 필드명 오해

### 문제

Sweetbook 템플릿 호출 시 업로드 파일 필드명을 SDK 예시처럼 고정값으로 넣으면 실패할 수 있습니다.

- 표지 템플릿은 `files`가 아니라 `coverPhoto`
- 선택한 A5 내지 템플릿은 `rowPhotos`가 아니라 `photos`

### 영향

이 값을 틀리면 다음과 같은 문제가 발생합니다.
- `Validation Error`가 발생하며 필수 파라미터 누락으로 처리됨
- 일부 경우에는 서버가 `500 Server Error`로 응답해 원인 파악이 더 어려워짐

### 원인 가설

파일 업로드 필드명은 템플릿 정의의 `parameters.definitions`에 있는 key를 따라야 합니다.

실제 확인한 A5 템플릿 예시:
- `1dTGvR4NivrD` 표지 템플릿: `coverPhoto`
- `1UbWOuoHeNkF` 내지 템플릿: `photos`
- `5ZpsyEJW5PZW` 내지 템플릿: `photos`

### 대응

- 서버 클라이언트의 기본 파일 필드명을 `coverPhoto`, `photos`로 수정
- 앞으로는 템플릿 UID를 바꿀 때 `definitions`를 함께 확인하는 규칙 유지

### 남은 리스크

- 다른 공개 템플릿을 채택하면 필드명이 다시 달라질 수 있음
- 장기적으로는 템플릿 정의를 동적으로 읽어 파일 필드명을 자동 결정하는 구조가 더 안전함

## 2026-04-05 비정상 테스트 이미지로 인한 서버 오류

### 문제

1x1 픽셀짜리 초소형 PNG로 표지/내지 템플릿을 호출했을 때 `500 Server Error`가 발생했습니다.

### 영향

- 템플릿 파라미터 문제인지 이미지 자체 문제인지 처음에는 구분이 어려웠음
- 잘못된 결론을 내리면 API 연동 자체가 깨진 것으로 오해할 수 있음

### 원인 가설

Sweetbook 렌더링 파이프라인이 지나치게 작은 비정상 이미지에 대해 내부 처리 오류를 내는 것으로 보입니다.

### 대응

- 240x180 PNG 테스트 이미지를 따로 만들어 다시 검증
- 동일한 템플릿과 올바른 파일 필드명으로 `cover`와 `content` 호출 성공 확인

### 남은 리스크

- 실제 사용자 업로드 이미지에 대한 최소 해상도 기준은 아직 별도 문서화되지 않음
- 프론트 업로드 단계에서 너무 작은 이미지를 사전에 차단하거나 경고하는 UX가 필요할 수 있음

## 2026-04-05 웹훅 secretKey 1회 노출 리스크

### 문제

Sweetbook 웹훅은 최초 등록 응답에서만 전체 `secretKey`를 반환하고, 이후 조회에서는 마스킹된 값만 제공합니다.

### 영향

- 최초 응답 시 값을 저장하지 못하면 나중에 서명 검증 구성을 다시 맞추기 어렵습니다.
- 운영 전환 시 웹훅이 계속 실패해도 원인을 바로 찾지 못할 수 있습니다.

### 원인 가설

공식 문서 기준으로 `PUT /webhooks/config` 최초 등록 시에만 전체 secret이 제공되고, 이후 조회는 보안상 앞부분만 노출되는 정책입니다.

### 대응

- `/ops/webhooks` 운영 패널에서 최초 응답의 `secretKey`를 바로 보여주도록 구성
- README와 운영 메모에 “발급 즉시 저장” 규칙 명시
- 수신 엔드포인트는 `timestamp.payload` 기준 HMAC-SHA256 검증 로직으로 고정

### 남은 리스크

- 개발 중 secret을 분실하면 재등록 또는 환경 변수 갱신이 필요할 수 있음
- 운영 환경에서는 secret 저장 위치와 접근 권한 정책을 별도로 정리해야 함

## 2026-04-05 주문 생성 시 즉시 차감 및 멱등성 누락 위험

### 문제

`POST /orders`는 `FINALIZED` 책만 허용하고, 주문 생성 시 충전금이 즉시 차감됩니다. 멱등성 제어 없이 재시도하면 이중 주문 또는 이중 차감으로 이어질 수 있습니다.

### 영향

- 프론트에서 중복 클릭이 발생하면 실제 비용 이슈로 이어질 수 있음
- 책이 FINALIZED 되지 않은 상태에서 주문 요청을 보내면 400 오류가 발생함

### 원인 가설

주문 API는 문서상 `Idempotency-Key` 헤더 사용을 강하게 요구하고, 유효성 검증 순서에서도 `bookUid` 존재와 FINALIZED 상태를 먼저 확인합니다.

### 대응

- 체크아웃 흐름에서 먼저 테스트 책 생성과 finalization을 끝낸 뒤 주문하도록 UX를 분리
- 주문 라우트에서 `items + shipping + externalUserId`만 해시해 안정적인 `Idempotency-Key`를 생성
- `externalRef`는 화면 재시도 때 값이 바뀔 수 있으므로 멱등성 해시 기준에서 제외
- 주문 화면에는 실제 차감이 일어나는 단계임을 명확히 안내

### 남은 리스크

- 동일한 payload 재시도는 안정적으로 막을 수 있지만, 주소나 메모를 바꿔 재주문하는 경우까지 세분화한 정책은 아직 별도 정의가 필요함
- 충전금 잔액 부족 시의 사용자 안내 문구와 복구 흐름은 아직 추가 개선 여지가 있음

## 2026-04-07 모바일 파일 선택 후 업로드 목록이 비지 않는 문제

### 문제

일부 모바일 브라우저에서 갤러리까지는 정상적으로 열리지만, 사진을 선택하고 돌아왔을 때 스텝 2의 선택 목록이 `0장`으로 남는 현상이 있었습니다.

### 영향

- 모바일 데모 플로우가 사실상 중단됨
- 사용자는 파일 선택이 실패한 것인지, 브라우저가 취소한 것인지 판단하기 어려움
- 스텝 2 이후 자동 정리와 포토북 생성까지 진행이 막힘

### 원인 가설

현재까지 가능성이 높은 원인은 두 가지입니다.

- 모바일 브라우저가 파일 피커 복귀 시 `input change` 이벤트를 안정적으로 다시 전달하지 않음
- 파일 피커에서 돌아오는 동안 페이지 포커스/가시성 전환이 생기며, 선택 상태 동기화가 누락됨
- 서버 로그가 비어 있었다는 점을 기준으로 보면, 실패 지점은 `/api/trips/intake` 요청 이전의 클라이언트 파일 선택 단계일 가능성이 높음

추가로 과거에는 다음 요소가 문제를 악화시켰습니다.

- 파일 선택 직후 `input.value = ""`를 바로 비우던 흐름
- 다크모드 감지를 위해 `pageshow` / `visibilitychange`를 반복 구독하던 로직
- `onChange`에서 받은 파일을 바로 쓰지 않고 `input.files`를 다시 읽어오던 우회 구조
- 하단 모바일 액션에서 비동기 지연과 중복 터치 처리로 사용자 제스처를 잃어버리던 구조

### 대응

- 스튜디오 업로드 단계에 `window focus` / `visibilitychange` 복귀 시 `input.files`를 다시 읽는 보조 동기화 로직 추가
- `input change` 외에 `input` 이벤트도 함께 구독
- 선택 직후 값을 바로 비우지 않고, 업로드 성공 또는 수동 초기화 시점에만 input 값 제거
- 스튜디오 화면에 `모바일 업로드 진단 로그` 패널을 추가해 실제로 어떤 이벤트까지 들어왔는지 확인 가능하게 함
- 상단 내비게이션을 햄버거 메뉴와 홈 링크 구조로 단순화해 모바일 복귀 시 경로 이동이 더 분명해지게 조정
- 파일 선택은 `onChange`에서 받은 `FileList`를 바로 상태에 반영하는 단일 경로로 단순화
- 파일 피커 복귀 시 `focus` / `visibilitychange` 기반 재동기화는 제거

### 남은 리스크

- 일부 브라우저는 파일 피커 복귀 시 `FileList` 자체를 늦게 채우거나 HEIC 미리보기 생성이 불안정할 수 있음
- 현재 수정은 진단과 복구 경로를 강화한 것이고, 특정 기기/브라우저 조합에 따라 추가 보정이 더 필요할 수 있음

## 2026-04-07 모바일 하단 액션이 사용자 제스처를 잃어버리는 문제

### 문제

하단 고정 액션 바에서 모바일 터치 입력을 별도 핸들러와 `setTimeout(0)`으로 감싸던 구조 때문에, 일부 액션이 모바일 브라우저의 사용자 제스처 컨텍스트를 잃을 수 있었습니다.

### 영향

- 파일 선택기 열기 같은 동작이 모바일에서 막히거나 불안정해질 수 있음
- 같은 버튼이 PC에서는 되는데 모바일에서만 반응이 약하거나 누락되는 현상이 생길 수 있음

### 원인 가설

모바일 브라우저는 파일 선택기, 포커스 이동 같은 동작을 보안상 직접 사용자 입력 안에서만 허용하는 경우가 많습니다. 비동기 지연이나 중복 터치 방지 로직이 이 맥락을 끊었을 가능성이 큽니다.

### 대응

- 하단 액션의 비동기 `setTimeout` 실행 제거
- `onTouchEnd` / `onPointerUp` 중복 처리 제거 후 `onClick` 중심으로 단순화
- 파일 선택 카드는 프로그램 클릭보다 실제 file input 오버레이를 직접 탭하는 방식으로 변경

### 남은 리스크

- 일부 브라우저에선 여전히 `showPicker()` 지원 여부 차이가 있을 수 있음
- 모바일 실기기에서 직접 검증이 계속 필요함

## 2026-04-07 Next 개발 서버가 모바일 브라우저에서 불안정하게 동작할 가능성

### 문제

모바일 실기기에서만 버튼 반응이 끊기거나, 업로드 단계 진단 로그가 한 줄도 찍히지 않거나, 자동 새로고침처럼 보이는 현상이 반복되었습니다.

### 영향

- 앱 코드가 아닌 개발 서버 런타임 문제를 앱 버그로 오인할 수 있음
- 특히 파일 선택 후 React 상태 반영과 같은 클라이언트 이벤트 검증이 크게 흔들림
- PC 브라우저에선 재현되지 않아 원인 분리가 어려워짐

### 원인 가설

현재 개발 서버는 `next dev` 기반이며, 모바일 브라우저에서는 Turbopack/HMR 웹소켓 연결이나 Fast Refresh 동작이 불안정할 가능성이 있습니다.

- 모바일에서만 주기적으로 화면이 다시 그려지는 체감이 있었음
- 업로드 단계에서 `useEffect` 기반 진단 로그조차 안 찍히는 경우가 있었음
- 사이드바/Back을 링크 중심으로 단순화하자 일부 증상이 줄어든 점을 보면, 앱 로직 외에 개발 런타임 개입 가능성이 큼

### 대응

- 모바일 실기기 검증용 스크립트를 별도로 추가
  - `npm run dev:mobile`
  - `npm run dev:mobile:https`
- 모바일 검증 시에는 `webpack + no-server-fast-refresh` 조합을 우선 사용
- 여전히 불안정하면 HTTPS 개발 서버로 한 번 더 확인

### 남은 리스크

- 모바일 브라우저 종류에 따라 로컬 개발 서버 웹소켓 정책 차이가 있을 수 있음
- 개발 모드에서만 나타나는 문제인지, 실제 프로덕션 빌드에서도 남는 문제인지 분리 확인이 필요함

## 2026-04-07 Next 개발 서버에서 LAN 주소 접속 시 업로드 상태가 비는 문제

### 문제

같은 PC에서도 `http://localhost:3000`으로 열면 비교적 정상인데, `http://192.168.0.20:3000` 같은 LAN 주소로 접속하면 파일 input에는 파일명이 보이지만 스텝 2의 `이번에 추가할 사진` 상태가 비는 현상이 재현됐습니다.

### 영향

- 모바일 실기기뿐 아니라 같은 브라우저의 LAN 접속 테스트도 신뢰도가 떨어졌음
- 서버 `/api/trips/intake` 로그가 비어 있어 서버 문제로 오해하기 쉬웠음
- 실제 프로덕션 이슈와 개발 서버/HMR 이슈를 구분하지 못하면 잘못된 방향으로 디버깅이 길어질 수 있음

### 원인 가설

현재까지는 앱 로직보다 `Next dev + LAN origin + 클라이언트 하이드레이션/리프레시` 조합이 더 유력합니다.

- 별도 Vite React 실험판에서는 같은 모바일 환경에서도 파일 선택과 카드 반영이 정상 동작했음
- Next 앱은 `localhost`와 LAN 주소에서 증상이 갈렸음
- production 빌드 기준으로는 문제 재현이 사라질 가능성이 높게 관측됨

### 대응

- `/studio`의 검색 파라미터 처리를 서버/클라이언트 경계에 맞게 다시 정리
- `/ops/webhooks`와 `/studio`에서 production 빌드를 막던 `useSearchParams` 구조를 `Suspense + client leaf` 형태로 수정
- 개발 모드 이슈와 별개로, 제출/실사용 기준 검증은 production 서버 기준으로 다시 확인하는 규칙 추가

### 남은 리스크

- `next dev` 상태에서 LAN 주소 실기기 검증은 여전히 오탐 가능성이 있음
- 실개발 중 업로드 UX를 확인할 때는 `localhost` 또는 production 서버 검증을 우선해야 함
